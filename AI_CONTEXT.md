# AI_CONTEXT — Grimoire Mod

## 1. Что это за проект

Minecraft-мод на **NeoForge 1.21.1** (Java 21, Gradle 8.14.4). Корневой пакет:
`com.example.grimoiremod`. Основное: система глифов/заклинаний, книга-гримуар,
верстак глифов, снаряды, дерево навыков.

Пакеты: `block, client, data, entity, glyphs, item, menu, network, util`.

## 2. ⚠️ ЖЁСТКИЕ ЛИМИТЫ ЧАТА И КАК ИХ ОБХОДИТЬ ⚠️

Веб-интерфейс **обрезает контекст**, если суммарный размер прикрепленных файлов в ОДНОМ сообщении превышает ~150-200 КБ. 
**НИКОГДА не проси пользователя прикреплять несколько частей дампа одновременно.** 
Если пользователь загрузит 3 файла по 70 КБ в одном сообщении, система отрежет последние 40% текста, и ты их не увидишь.

**ПРАВИЛО ИНКРЕМЕНТАЛЬНОЙ ЗАГРУЗКИ:**
Если требуется полный контекст проекта (или дамп разбит на части `part_00.txt`, `part_01.txt` и т.д.), ты должен запрашивать их **строго по одному файлу за сообщение**.

## 3. Инструменты

### `apply_update.sh` (обёртка)
Запускает: `apply_update_body.sh` → `compileJava` → `dump_project.sh` → `runClient`.

### `apply_update_body.sh` — твой ВЫХОД
Bash-скрипт с heredoc'ами. Никаких патчей и диффов. Только полные файлы.
Обязательный формат:
~~~bash
cat > 'src/main/java/com/example/grimoiremod/SomeFile.java' <<'EOF_SRC'
... ПОЛНОЕ содержимое файла ...
EOF_SRC
~~~
Правила:
- `'EOF_SRC'` всегда в кавычках.
- Всегда полное содержимое файла, не фрагмент.
- Запрещено: `git`, `patch`, `diff`, `apply`, `sed -i`.
- Запрещено: вызывать `./gradlew` (обёртка сама вызовет).
- В конце: `echo "OK: N files written"`.

### `dump_project.sh` — генератор контекста
Третий аргумент — папка для Java-файлов.
- `./dump_project.sh d.txt java src/main/java/com/example/grimoiremod/client` — только client
- `./dump_project.sh d.txt java src/main/java/com/example/grimoiremod/glyphs` — только glyphs
- `./dump_project.sh d.txt config` — только конфиги/ресурсы (без java)
- Если дамп делается целиком, скрипт рубит его на `part_00.txt`, `part_01.txt` и т.д. по 70 КБ.

### ⚠️ Как правильно показывать `apply_update_body.sh` в ответе

Если `apply_update_body.sh` пишет файлы, **внутри которых есть markdown-фенсы** (типичный случай: `README.md` с блоками кода) — сам скрипт в чате нужно оборачивать в **4 (четыре)** обратные кавычки, а не в 3. 

**Причина:** внутренние тройные фенсы «закрывают» внешний блок раньше времени. Пользователь копирует обрезанный или повреждённый текст — .sh ломается, файл не применяется.

**Правило:** если внутри тела `apply_update_body.sh` встречаются тройные обратные кавычки — **внешний фенс в ответе делай 4-кратным**. 
**Альтернатива (самая безопасная):** вообще не использовать обратные кавычки внутри файлов (заменять их на тильды `~~~`), а сам ответ оборачивать в 4 обратные кавычки.
**КРИТИЧЕСКИ ВАЖНО (Heredoc Collision):** никогда не используйте разделитель (delimiter), который может встретиться в тексте файла. Если вы пишете в файл `AI_CONTEXT.md`, в котором есть пример с `EOF_SRC`, и используете `EOF_SRC` как разделитель — bash закроет файл на середине. Всегда используйте уникальные разделители (например, `EOF_AI_CONTEXT` для `AI_CONTEXT.md`).

## 4. Протокол (снайперский режим)

### Сценарий А: Точечный запрос (ПРИОРИТЕТНЫЙ)
Если задача касается конкретной системы (например, GUI, логика или сеть):
1. Пользователь присылает задачу.
2. Твой ответ — запрос ОДНОГО дампа нужной папки:
   ~~~
   DUMP REQUEST:
   ./dump_project.sh d.txt java src/main/java/com/example/grimoiremod/<package>
   ~~~
3. Пользователь присылает дамп.
4. Твой ответ — `apply_update_body.sh`.

### Сценарий Б: Полный контекст

⚠️ **ГЛАВНОЕ ПРАВИЛО: НЕ АНАЛИЗИРУЙ, НЕ ОЦЕНИВАЙ И НЕ ПИШИ `apply_update_body.sh`, ПОКА НЕ ПОЛУЧЕНЫ ВСЕ ЧАСТИ ДАМПА.**

Количество частей **заранее неизвестно** — их может быть 2, 3, 5, 10. Ты не знаешь, сколько их, пока пользователь явно не скажет «это последняя часть» / «это всё» / не пришлёт все.

1. Ты просишь пользователя запустить `./dump_project.sh`. Скрипт разобьёт проект на части.
2. Ты пишешь: **"Прикрепи только `part_00.txt`"**.
3. Пользователь присылает `part_00.txt`.
4. Ты отвечаешь **строго коротким подтверждением**: **"Получил part_00. Прикрепи `part_01.txt`"**.
   - **НИКАКОГО анализа, оценок, замечаний, баллов, «предварительных» выводов.**
   - Даже если ты уже видишь баги в part_00 — молчи. Это часть более широкой картины.
5. Повторяй шаг 4 для каждой следующей части (`part_02`, `part_03`, ...), пока пользователь не напишет **«это последняя часть»** или **«это всё»**.
6. **Только после этого** — анализ, замечания и `apply_update_body.sh`.

**Чек-лист перед началом анализа (проверь все пункты):**
- [ ] Пользователь явно подтвердил, что это последняя часть дампа (или прислал все известные ему части).
- [ ] Все файлы, которые ты ожидал увидеть, присутствуют целиком (нет обрывов на середине метода/файла).
- [ ] Если ты видишь обрыв на середине файла (последняя строка — `@Override`, `...` или незакрытая скобка) — это **НЕ последняя часть**, продолжай запрашивать.
- [ ] Ты не начал анализ после `part_00`, `part_01` и т.д. раньше времени.

**Пример правильного диалога:**
> Пользователь: [part_00.txt]
> AI: Получил part_00. Прикрепи part_01.txt.
> Пользователь: [part_01.txt]
> AI: Получил part_01. Прикрепи part_02.txt.
> Пользователь: [part_02.txt] Это последняя.
> AI: Получил все части. Приступаю к анализу. [дальше анализ и код]

**Пример НЕПРАВИЛЬНОГО диалога (так делать нельзя):**
> Пользователь: [part_00.txt]
> AI: Оцениваю проект по part_00: архитектура 8/10, но вот баги... [НАРУШЕНИЕ]
